# Discord参照の性能調査

2026-10-31のコード調査と、制御時計・偽のDiscord応答による再現結果。
実環境のDiscordトークンが作業環境にないため、実通信の所要時間は未測定。

## 修正した要因

- MCPは履歴のページを取得するたびに、チャンネル所属確認GETも実行していた。同じチャンネル10ページで20 GETだったものを、所属情報の60秒キャッシュにより11 GETに削減。本文・権限エラーはキャッシュしない。
- レート制限ヘッダーがない応答では、そのルートだけでなく全リクエストに2秒待機を設定していた。所属確認の直後の本文取得や、無関係なチャンネルも停止する。当初は全体への波及のみ除去していたが、現在は人工的な2秒待機自体を廃止。
- 個別メッセージ取得では、チャンネル単位であるべきbucketのmajorキーにメッセージIDを含めていた。別IDを読むと別bucketとして扱われるため、チャンネル単位に修正。これは高速化ではなく、Discordの制限を正しく守るための修正。

ヘッダーなし・同じチャンネルを10ページ読むケースを再現したところ、意図的な待機時間は旧処理38秒、新処理0.20秒（10ページ+所属確認1回、全体50req/s）。これは通信・画像転送・RAG検索・LLM生成時間を除いたテスト上の値であり、本番の応答時間が同率で短くなるという測定ではない。`tests/test_discord_mcp.py::test_history_paging_wait_time_before_and_after` で再現できる。

## 履歴0件で止まる不具合と修正

ライブ発言の保存と過去ログの走査が同じカーソルを更新していた。ライブ発言を1件保存するとカーソルが最新へ進み、その後の `after` 取得が空になり、未取得の古いログを飛ばしていた。走査専用の新テーブルを設け、APIから読み取り・保存が完了したページだけ位置を確定する。旧テーブルの位置は継承せず、初回に過去分を再確認して取りこぼしを回収する。既存の発言IDにより重複Embeddingは防ぐ。

また、実装には起動時・定期巡回がなく、新着発言が来たチャンネルだけが取得対象だった。Bot接続時と60秒ごとに、閲覧・履歴参照権限があるチャンネルと把握済みスレッドを巡回する。進行中のチャンネルは巡回で重複予約しない。停止時は巡回タスクを終了し、受付済みの取り込みはdrainする。

独自の25req/s・bucket使用率50%も廃止した。全体50req/s以内で予約し、各bucketの残量がある間は取得、残量0でリセットまで待つ。並行要求も残り枠を予約してから送る。429の待機は維持する。Bot本体SDKや別プロセスの呼び出しは同じ制限器で予約されないため、Discord側での競合時は429に従う。

## 残る時間の切り分け

INFOログで本文やトークンを出さずに以下を記録する。

| ログ | 計測対象 |
| --- | --- |
| `Discord API GET` の `wait_seconds` | 既存のレート制限器による待機 |
| 同 `request_seconds` / `status` | HTTP通信時間と応答ステータス |
| `Discord MCP` の `read_seconds` | MCPツール内のDiscord読み取り全体 |
| 同 `image_seconds` / `images` | 添付画像のダウンロード・変換時間と枚数 |
| `LLM response` の `seconds` / `round` | ツールの選択や最終回答を生成するモデル時間 |

モデルがページングを繰り返すと、そのたびにLLM生成が必要になる。長い返信チェーンの未キャッシュ発言も、参照先が分かってから順にDiscord APIで取得する。これらは今回の修正後も残る。MCPのHTTPクライアントは呼び出し単位で生成するため、呼び出しをまたぐ接続再利用も未実装。まず上のログで本番の内訳を確認し、実測で支配的な部分を次の最適化対象にする。
